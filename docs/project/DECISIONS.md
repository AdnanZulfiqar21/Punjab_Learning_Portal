| RESCAN-01 | 2026-10-08 | **Learner actions on pending questions: readability rescans, reviewed classification, confirmed-unanswered and a 7-day deadline (W04.S3.T2, W06.S2.T4, §20.7.3, §20.6.3, §20.10; WA-AC62/63/82).** A teacher may leave a question pending and ask the learner to act: `rescan` (unreadable) or `confirm_or_rescan` (mapped evidence looks blank). Only this request's own objects are cleaned up. Positions not named were marked from the sealed original, which stays allowed even when another copy is NEW_CONTENT or INDETERMINATE. Provenance carries forward through rechecks and completion publications for questions they don't change. | ADJ-01 | 2026-10-08 | **Rubric adjudications across attempts (W06.S2.T3; §20.10; WA-AC26/64/77/78).** A rubric correction is made through the editorial workflow (revise, review, publish), so new forms use it. Applying it to work already started or marked is a separate, audited decision. An academic adjudicator in the item's class and subject creates a `written_rubric_adjudication` naming the superseded rubric versions it corrects (default: every earlier published version for the same question version), the corrected published version and a reason (20+ characters). **Compatibility is computed, never supplied by the client:** a per-criterion diff over the fields that decide a mark (subpart, description, maximum, levels, dependencies, alternative group) plus rubric-level scoring rules. *Carry forward* only when all of these are identical, i.e. only reviewer notes such as expected concepts changed. **Compatible denominators:** every slot maximum must match (`INCOMPATIBLE_DENOMINATOR` otherwise; a different total is a question change). **Effective set:** active corrections chain (A→B, B→C) and the target is the end of the chain, so each run applies the complete approved set and jobs converge. A correction that claims a version already claimed by an active one must name it in `supersedes_id` (`SUPERSEDE_REQUIRED`), which marks the earlier one superseded; creation is serialised per rubric with an advisory lock. **Regrade job** (`POST …/adjudications/{id}/run`, `portal-written-regrade`): bounded batches, one short transaction per attempt (attempt row lock, then that attempt's queued cases), resumable and idempotent through a `written_rubric_regrade` row per (adjudication, attempt). Per affected question: *scored + identical scoring basis* → a new released version with identical marks re-based onto the corrected rubric, `decision_method=SYSTEM`, `case_kind=regrade`, with `regrade_detail` recording the carried human decisions and compatibility evidence (never labelled TEACHER). *Scored + changed basis* → never recomputed by machine; a queued `regrade` case asks a teacher to re-mark under the corrected rubric, and the released result stays until that teacher releases. If an open case (e.g. a recheck) already covers the question it is re-targeted instead, with its version bumped so a stale save conflicts. *Pending, unavailable or not yet marked* → re-targeted for later marking (`written_rubric_target`; `case_context` uses it). Regrade decisions may only score the case's questions, and publication still goes through the existing lease, expected-version and base-version checks. Each affected learner gets one deduplicated `written_notice` per correction, shown on the result; history labels the regrade. Nothing consumes or releases allowance; evidence, earlier versions and forms are never edited. *Evidence:* `tests/test_rubric_adjudication.py` (5, real PostgreSQL): carry-forward once with SYSTEM label and identical marks, idempotent re-run, adjudicator-only creation; changed basis goes to a teacher, the result is held, the case shows the corrected rubric, pending is refused, TEACHER release; retargeting of unmarked and pending questions through a chain, explicit supersede; two concurrent runs regrade each attempt once; an open recheck re-targeted rather than duplicated. Studio pages: list, create from the corrected rubric's page, impact preview, run next batch; seeded dev adjudicator `studio-adjudicator@example.com`; E2E smoke for adjudicator access. | Engineering (roadmap W06.S2.T3) | No browser journey for the full correction/regrade flow yet (API-tested); automatic (AI) regrades don't exist; notifications beyond the in-result notice (P15.S1); deployment must run `portal-written-regrade` or the studio button after each approved correction. |
