| IMPL-13 | 2026-10-07 | **Native session handling.** The app exchanges an IdP access token for a `native` app session (60 days / 30 idle, IMPL-12). The session token is stored only through `expo-secure-store` (Android Keystore / iOS Keychain, `WHEN_UNLOCKED_THIS_DEVICE_ONLY`), never in AsyncStorage or logs. At start-up the app validates it with `/v1/me`. A 401 anywhere (expired, or revoked from another device) clears it and returns to sign-in. Offline start-up keeps the token and offers a retry. Sign-out revokes the session on the server and always clears it locally, even offline. The Account tab offers sign-in (only the methods `runtime-config` advertises), profile summary, signed-in devices, revoke one, revoke others and sign-out. Onboarding is a stack screen with the same fields as web and no ID documents. The Expo **web** target stores the token in `sessionStorage` for development preview only. *Evidence (Expo web target, functional only; not native evidence):* register → native session → onboarding saved → profile shown; a reload keeps the session; revoke-others from the app kills the other session (401); revoke from another device signs the app out on next load; a wrong password shows the generic error; sign-out → server 401 and storage cleared. | Engineering (roadmap §5.3, P04.S1.T2) | Keystore behaviour on a device is unverified until B13/B07. OIDC PKCE needs B04. |
| IMPL-12 | 2026-10-07 | **App sessions on top of IdP tokens.** `POST /v1/sessions` accepts only a verified IdP access token (never another session) and returns an opaque `pls_` token. Only its SHA-256 is stored (`user_sessions`). Lifetimes: web 30 days absolute / 7 days idle; native 60 / 30. Users can list their sessions, revoke one (someone else's session ID → 404), revoke all others, or sign out. Revoked, expired or idle sessions → 401. **Web is a backend-for-frontend:** the token lives only in an HTTP-only `portal_session` cookie (SameSite=Lax, `Secure` in staging/production) and Next.js server code forwards it as a Bearer token; browser JavaScript never sees it. Mutations are Server Actions (POST only, Origin/Host checked by Next.js), and `next` return paths accept only same-site relative paths. Protected pages (`/account`, `/onboarding`) validate the session with the API and redirect to `/signin?next=…`. The header shows Sign in/Account from cookie presence only, so it never waits on the API. Onboarding never asks for CNIC or ID documents. *Evidence:* `apps/api/tests/test_sessions.py`; `apps/web/e2e/auth.spec.ts` (register → onboarding → profile → sessions → sign-out, protected redirects, wrong password, cross-device revoke, open-redirect refusal), 88/88 runs with `--repeat-each=4`. | Engineering (roadmap §5, P04.S1.T2/P04.S3.T1) | Web OIDC redirect (PKCE) and native secure storage need the B04 tenant; the dev adapter covers development and test only. |

| IMPL-08 | 2026-10-07 | **Stable catalogue identity.** `content/catalogue/id_registry.json` is the authority for entity IDs. Rebuilds reconcile within the same parent: explicit override (`id_overrides.json`) → same key/alias → same printed number → same or similar title (≥0.85, unambiguous) → otherwise a new ID. Title, number and numbered/unnumbered corrections keep IDs, and old keys become aliases. Unmatched entities are **retired** (registry `status=retired`; database `retired_at`), never deleted. They are hidden from learners (lists, topics, search, prev/next), a retired chapter returns **410 Gone**, and re-adding reactivates the same ID. Imports never reset academic `content_state`. Active display-order uniqueness is a partial index, and imports shift orders inside the transaction. *Evidence:* bootstrap preserved all 1,990 existing IDs (0 new, 0 retired). The local dev DB was migrated and re-imported **without reset** (0 new, 0 retired, 0 reactivated). Tests: `content/tools/test_identity.py` (8) and `apps/api/tests/test_catalogue_identity.py` (corrections, removals, reorder, reactivation on a populated database). | Engineering | Moving a topic to a different chapter creates a new ID unless an override maps it. |
| IMPL-07 | 2026-10-07 | **Identity design.** The API verifies every access token the same way: RS256 signature via JWKS, issuer, audience (`aud` or Cognito `client_id`), expiry, and `token_use=access`. MFA comes from `amr`. Users are keyed by (issuer, subject) and created idempotently on the first verified request (no trial side effects). Roles are app-owned, scoped grants that are revoked, never deleted, and audited. Sensitive permissions (publish, quarantine, adjudicate, finance, operate, manage roles, audit) need an MFA session. Admins cannot change their own roles. The first owner is bootstrapped with the audited `portal-grant-role` CLI. A **dev-only local issuer** (email + argon2 password, ephemeral keys) stands in for Cognito (B04). It is refused in staging/production, hidden from the OpenAPI contract, and its responses are enumeration-safe. | Engineering (roadmap §4, §5, P04) | Web cookie/BFF session and native PKCE flows are next (P04.S1.T2). Live verification needs the B04 tenant. |

| IMPL-05 (rev. 2026-10-07) | 2026-10-07 | **Not-found/error semantics, measured on Next 16.4.0 with `cacheComponents: true`, `partialPrefetching: true`:** (1) URL matching no route (`/no-such-page`, `/learn/11/biology/extra/segment`) → **HTTP 404**, not-found page, `noindex`. (2) Route matches but the catalogue record doesn't exist or is out of scope (`/learn/11/english`, an unknown chapter UUID, a malformed chapter ID) → `notFound()` runs inside the streamed Suspense boundary after the shell, so **HTTP 200** + not-found page + `noindex`. No experimental dependency was added to change (2)-(4). | Engineering | E2E asserts (1) status 404 and (2) noindex + not-found UI. |
