### OCT14-01 — Pending pages do not prevent submission

Source: [native written runner](https://github.com/AdnanZulfiqar21/Punjab_Learning_Portal/blob/5162ca4b86f840ae195107d4331d9a1849ca906f/apps/mobile/src/app/written/[id].tsx), particularly `Runner`, `seal`, pending-page rendering and the submit button.

The submit button checks mapping completeness and `saving`. The handler does not guard against pending uploads or failed local pages. Once the server returns a non-active attempt, the remounted runner calls `clearAttempt`.

Reproducible scenario to turn into a component test:

1. Upload page A and map all required answer slots.
2. Capture page B containing further working. Its upload fails, leaving it in the local pending list.
3. “Submit for marking” remains enabled because the slots were already mapped.
4. Submission seals the server's current manifest without page B.
5. The sealed runner removes the attempt's local draft directory.

The server cannot include a page it has never received. The danger is the client allowing final submission and then silently deleting the unsent work.

**Required correction**

- Block submission whenever capture, upload, retry or page mutation is in progress, and whenever unsent pages remain.
- Guard inside `seal()` as well as in the button state; prevent a concurrent pick/capture action from slipping past a stale render.
- Give the learner a clear route to retry or explicitly discard an unwanted pending page.
- Do not interpret “attempt closed” as proof that every local page was uploaded. Handle remaining local work under the documented retention/discard policy.
- Preserve server revision checking and the stable submission idempotency key.

**Acceptance:** all slots mapped + one failed/pending page cannot seal; a concurrent capture cannot bypass the gate; after successful upload or explicit discard, submission works once; a lost submission response recovers the same receipt.

### OCT14-02 — Failure transitions are not fenced by the worker claim

Source: [bulk imports](https://github.com/AdnanZulfiqar21/Punjab_Learning_Portal/blob/5162ca4b86f840ae195107d4331d9a1849ca906f/apps/api/src/portal_api/modules/content/bulk_imports.py), `_claim`, `_locked`, `_fail`, `_check_rows`, `_commit_rows`.

Normal progress uses `_locked(..., owner, status)`. In contrast, `_fail(db, batch_id, reason)` only locks by ID. It does not verify the claim owner or expected status before deleting the upload and setting the batch to failed.

Failure path:

1. Worker A claims validation and pauses before reading the file.
2. Its two-minute lease expires; B reclaims the batch and finishes the preview, deleting the raw upload.
3. A resumes, cannot read its old file path, and invokes `_fail`.
4. A can replace the previewed state with failed. A later committed state is also not protected by this helper.

The isolated probe called the unchanged helper with rows owned by another worker. It changed **validating**, **previewed** and **committed** to **failed**, cleared the lease and file key. This is not a PostgreSQL race test; the missing guard is directly demonstrated.

**Required correction**

- Fence every mutation, including failure, cleanup and audit, with the expected state and a current claim token/generation.
- A stale worker must return “stopped” without touching another worker's file or result.
- Keep file cleanup recoverable and tied to the successful state transition; do not delete files before proving ownership.
- Review identity-map freshness and the rollback-to-failure gap when implementing the transaction boundary.

**Acceptance:** a deterministic two-session PostgreSQL test pauses A, reclaims with B, then resumes A. B's preview/commit and audit remain unchanged; stale A cannot remove B's raw file or mark the batch failed.

### OCT14-03 — A damaged workbook can crash the queue worker

Sources: [XLSX parser](https://github.com/AdnanZulfiqar21/Punjab_Learning_Portal/blob/5162ca4b86f840ae195107d4331d9a1849ca906f/apps/api/src/portal_api/modules/content/imports.py), `_optional` and `xlsx_table`; [worker](https://github.com/AdnanZulfiqar21/Punjab_Learning_Portal/blob/5162ca4b86f840ae195107d4331d9a1849ca906f/apps/api/src/portal_api/modules/content/bulk_imports.py), `_check_rows`, `work`, `worker_main`.

Opening the outer ZIP catches `BadZipFile`, but member reads only catch `KeyError`. A CRC error during member reading raises `zipfile.BadZipFile`, which is not an application error. The worker catches only `AppError` around parsing, and the queue drain has no exception isolation.

The local probe took the repository's generated XLSX template, changed one stored workbook byte without updating the CRC, and ran the unchanged parser:

```text
BadZipFile: Bad CRC-32 for file 'xl/workbook.xml'
caught_by_AppError: false
worker drain: BadZipFile escapes; batch status remains validating
```

A damaged upload can therefore stop that worker run, leaving the same job eligible for another failing attempt after lease expiry. A healthy later job is not reached in that drain.

**Required correction**

- Normalize corrupt member, unsupported compression and encrypted member failures into bounded validation errors.
- Apply consistent archive error handling to media-pack `manifest.json` as well; its outer ZIP can open while its manifest member is unreadable.
- Isolate jobs so a bad input cannot terminate all queue processing.
- Distinguish permanent input failures from retryable service/database/storage failures; use bounded retries and observability. Do not swallow every exception or call work successful.
- Combine error handling with OCT14-02's ownership fencing.

**Acceptance:** corrupt, encrypted and unsupported workbooks terminate with a useful failure status; a valid following batch succeeds; no partial content commit; no restart loop for a poison input. Test corruption of a media manifest separately.

### OCT14-04 — Error-note persistence can destroy recoverable work

Source: [native page draft storage](https://github.com/AdnanZulfiqar21/Punjab_Learning_Portal/blob/5162ca4b86f840ae195107d4331d9a1849ca906f/apps/mobile/src/lib/page-drafts.ts), `notePageError` and `listPages`.

`notePageError` overwrites the only JSON record in place and catches write errors. The comment says only the error note is lost. But an interrupted/truncated metadata write leaves invalid JSON. `listPages` deletes invalid JSON; on a subsequent scan it deletes the raw page as an orphan.

The unchanged TypeScript functions, transpiled on the host and supplied a mocked filesystem that truncates a metadata write then raises an I/O failure, produced:

```text
before: 1 recoverable page
first recovery scan: 0 pages; raw image still exists
second recovery scan: 0 pages; raw image deleted
```

This demonstrates the recovery algorithm's response to corrupted metadata. It does not prove the precise interruption behavior of Expo's filesystem on every device.

**Required correction**

- Preserve immutable capture metadata; keep mutable upload/error state separately or replace metadata through a verified recoverable write protocol.
- Do not delete an otherwise usable unsent page merely because its sidecar cannot be parsed.
- Validate recovered metadata, quarantine/recover damaged records and show an actionable recovery state.
- A failure to save an error message must never convert an existing usable draft into an automatic deletion candidate.

**Acceptance:** fault injection around copy, metadata write/update and recovery preserves the previously saved raw page and enough information to recover it. Include repeated reopen, low-space, retry and explicit-discard tests. Real-device interruption testing remains required afterward.

### OCT14-05 — Queued writes bypass current account status

Sources: [worker actor](https://github.com/AdnanZulfiqar21/Punjab_Learning_Portal/blob/5162ca4b86f840ae195107d4331d9a1849ca906f/apps/api/src/portal_api/modules/content/bulk_imports.py), `_actor`; [scoped roles](https://github.com/AdnanZulfiqar21/Punjab_Learning_Portal/blob/5162ca4b86f840ae195107d4331d9a1849ca906f/apps/api/src/portal_api/modules/content/workflow.py), `roles_in_scope`; [identity checks](https://github.com/AdnanZulfiqar21/Punjab_Learning_Portal/blob/5162ca4b86f840ae195107d4331d9a1849ca906f/apps/api/src/portal_api/modules/identity/deps.py); [suspension route](https://github.com/AdnanZulfiqar21/Punjab_Learning_Portal/blob/5162ca4b86f840ae195107d4331d9a1849ca906f/apps/api/src/portal_api/modules/identity/router.py).

HTTP authentication rejects any account whose status is not active. Suspending an account revokes sessions and changes its status, but does not revoke its staff grants. The background worker constructs an actor from the user row without checking status; import validation checks those grants.

Consequently an author can queue a commit, be suspended before the worker starts it, and still have the worker write the draft content under that identity. The helper probe returned actors for both suspended and deleted fixture users. A full database commit reproduction remains to be added.

**Required correction**

- Validate current account eligibility as well as current scoped permission at the background write boundary.
- Do not fabricate a live authenticated session for a job. Define explicit background authorization and auditing.
- Refresh authorization at appropriate transaction/chunk boundaries; the current validation scope cache survives chunk commits.
- Keep already committed work intact and record why unstarted/remaining work was denied.
- If the product intentionally permits some authorized jobs to outlive suspension, define and approve that exception explicitly; do not infer it from missing checks.

**Acceptance:** queue a valid commit, suspend the author, run the worker, and assert no new content rows. Also cover revoked scope, active authorized success and deterministic handling of reinstatement.

### OCT14-06 — XML declaration guard is encoding-dependent

Source: [XLSX XML parsing](https://github.com/AdnanZulfiqar21/Punjab_Learning_Portal/blob/5162ca4b86f840ae195107d4331d9a1849ca906f/apps/api/src/portal_api/modules/content/imports.py), `_DECLARATION` and `_optional`.

The raw-byte regex searches for ASCII `<!DOCTYPE` or `<!ENTITY`. UTF-16 represents these tokens with interleaved bytes, so they do not match. ElementTree accepts that encoding and expands a small internal entity.

A bounded local probe (no external references and no large expansion) returned:

```text
byte_guard_matched: false
parsed_text: probe-expanded
```

The claim that DOCTYPE/entities never reach the parser is therefore false. This probe does **not** establish external-file access, network access, or an unbounded entity-expansion exploit.

**Required correction**

- Use a parser configuration/library that rejects DTD/entity declarations independently of XML encoding, or a strictly defined encoding pipeline with equivalent enforcement.
- Do not solve this with one more encoding-specific regex.
- Preserve size/depth limits and normalize parser errors into the import's validation result.

**Acceptance:** UTF-8 and UTF-16 declarations are rejected consistently; ordinary supported workbooks still parse; the queue survives invalid input.
